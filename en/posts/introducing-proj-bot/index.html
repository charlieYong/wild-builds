proj-bot: A Team Assistant for Product, QA, and Engineering

charlie · 2026-11-14· English

A work assistant inside the team

proj-bot is a work assistant in the team's Feishu workspace. Members describe a task in a conversation; the model interprets the goal and selects tools, while the host checks execution eligibility. The Bot returns answers, operation results, or files.

Who uses it Work they delegate What they receive
Product planning Look up rules, find configuration, and check activation conditions Explanations tied to configuration and implementation logic
QA Prepare test state and compare screenshots with data Operation results, state readbacks, and explanations of differences
Engineering Investigate defects and inspect duplicate-request handling Analysis tied to a source revision and issue reports

These requests are specific, but answering them spans documents, configuration, environments, and code. We built proj-bot so members can state a goal in one place and delegate the repeated work of finding tools, connecting steps, and assembling results.

Core design: the model selects tools; the host controls execution

The model interprets requests and selects capabilities. A host service outside the model process checks execution eligibility. The Feishu integration supplies trusted session identity. A wrapper injects current context on each turn, while SQLite stores the target, state, and task version, which changes as task information is updated.

Main business calls, such as diagnosis and operations, must pass host-side task checks. The version check prevents calls prepared for an old task target from being reused after the target changes. Queries used to find an account or fill in missing information have separate entry points; they do not grant write eligibility.

Condition checked Host behavior
Required task information is missing, or the supplied task version is stale Reject the call until information is supplied or the task is reconfirmed
The task is not an operation task in the running state, or the target permits reads only Reject the write

Writes also coordinate by environment and resource scope. Conflicts cause a wait or a busy response. Code analysis uses read-only views generated for specific commits, avoiding competing tasks that switch one shared working directory.

The tradeoff is explicit binding and additional checks. New tools need to integrate with host constraints. A new source commit requires a prepared view; tasks on the same commit reuse an existing one. Native tools continue to maintain business rules.

What one test request returns

One actual request asked the Bot to set a duration parameter on a test account to 7.99 seconds. The task reply reported:

Delivery item Content reported in the reply
Operation target Test environment, account, and the uniquely identified target instance
Value change 6084 → 7990 milliseconds
Readback after logging in again Seven related values, all at 7990 milliseconds
Backups Locations of before-and-after backup files

Recorded usage

From October 17 to November 13, 2026, the entry point recorded 38 accounts and 838 new tasks, averaging about 30 new tasks per day; 614 tasks were marked completed. These records do not fully separate historical self-tests, and completed denotes task state only. From November 7 to 13, 26 accounts submitted 284 tasks.
