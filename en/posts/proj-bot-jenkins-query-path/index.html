The Bot Had Jenkins Tools. Why Couldn’t It Read a Build?

charlie · 2026-11-16· English

A request to investigate an automatic deployment that had not taken effect left proj-bot stuck at the build query. The project already had Jenkins scripts, and the Bot found related entry points. Yet it first hit missing environment configuration, then received:

Tunnel connection failed: 403 Forbidden

proj-bot is a work assistant in the team’s Feishu workspace. Members describe a goal in natural language; the model selects tools, and the host checks execution eligibility. This failure exposed a gap between those layers: an existing project tool still needed a complete path for the Bot to use it in a read-only investigation.

Two failures at different points

During this investigation on November 12, 2026, the Bot first ran a deployment script’s status query inside a general tool sandbox. The script needed environment configuration, but the query reported that the required configuration directory was missing and stopped during preparation.

The Bot then tried reading Jenkins directly and received a 403 while establishing a proxy tunnel. That is different from Jenkins receiving the query and deciding that the account cannot read it.

Attempt Observed result What to examine next
Query status inside the general tool sandbox Missing environment configuration directory Execution location, mounted files, and configuration resolution
Access Jenkins through the proxy Tunnel connection failed: 403 Forbidden The CONNECT request and host-side connection authorization

These failures need separate fixes. Providing configuration does not establish network access. Changing how an HTTP request is made does not supply the missing environment mapping.

Identify the source of the 403

An HTTPS client using an HTTP proxy normally sends CONNECT first, asking the proxy to establish a tunnel. Only after that succeeds does the client exchange HTTPS data with the upstream service. RFC 9110’s CONNECT definition distinguishes successful tunnel establishment from failure.

The proxy implementation at the time converted a host-side connection denial into HTTP 403. Together with the tunnel exception, this pointed the investigation toward connection authorization. The error alone did not establish whether the Jenkins account had read access.

To examine the distinction, I ran a local experiment with Python 3.9.6: an HTTPS service and a CONNECT proxy with switchable behavior. The service used a local certificate, which the client verified. Each case recorded the client result and the number of HTTP requests received upstream.

Local experiment condition Client result Upstream HTTP requests
Proxy rejects CONNECT Tunnel error, 403 0
Proxy allows the tunnel; upstream rejects authentication HTTP 401 1
Proxy allows the tunnel; authentication succeeds; build failed HTTP 200, result=FAILURE 1

The third case matters too: a successful query can return a failed build. Transport, query access, and build outcome need separate explanations. This local experiment demonstrates the mechanism; it does not measure how many upstream requests occurred in the historical incident.

Add an explicit path for read-only investigation

At the time, the existing remote deployment entry point performed write checks, while the status entry point followed the service runtime-status workflow. Neither directly supplied build-list or build-log queries.

The change added build-list, individual-build, build-log, and queue queries to the controlled remote entry point and delegated execution to the native Jenkins query script. The Bot adapter handled session identity, task version, and environment binding. This task version changes as task information is updated, allowing calls based on stale task state to be rejected. The native tool retained environment-to-job mapping, credential resolution, and API requests.

Two constraints make that path concrete.

First, the environment comes from the bound task. The adapter rejects attempts to override the environment, host, service, or action through forwarded arguments. A call prepared in one task’s context must not quietly select another target.

Second, build queries use read checks, while deployment retains write checks. Reading a build record should not require permission to trigger a deployment, and query access should not grant deployment access. Jenkins’ remote API supports both retrieving information and triggering builds; the Bot entry point must preserve that distinction.

The cost is explicit integration: each additional action needs defined parameters and permission semantics. In return, environment mapping and Jenkins-specific rules keep a clear maintenance owner, and the model does not have to assemble a new connection method during every investigation.

Be precise about what acceptance established

In the live read-only acceptance run after integration on November 12, a program called the controlled entry point directly under an ordinary member’s identity and retrieved one Jenkins build record. It established that this entry point, target mapping, and read request worked together at that time. This read did not cover natural-language tool selection, write rejection, or target-override tests. It also did not establish that every build-log endpoint worked or that the original automatic deployment issue was fixed.

The investigation left me with a practical order: establish where the tool runs and which configuration it needs, identify the layer where the connection fails, then check the actual query and business outcome. A script in the project is an available capability. Making it usable by a team assistant also requires a clear path connecting execution location, target, and permissions.
