How Can an Agent Resume After Model Overload Without Repeating a Write?

charlie · 2026-11-21· English

If the model is overloaded after a tool has already written data, retry the failed model request with the original tool result. If the retries run out, keep the session so the user can resume in the same chat thread. Both recovery paths pick up after the completed write.

proj-bot used to end the current turn when the model reported a capacity error. While investigating, we found a production trace that ended with server_overloaded after several tool calls had already returned results. The trace showed that tool results existed. Whether a particular write took effect still depended on the target system. To isolate the question, we ran a countable write against a temporary file and injected overload into the very next model request.

Retry the model request inside the current turn

A turn with tool calls can span several model requests. The model asks for a tool call, the runner completes the write, and then the runner sends the result in another request. If that request hits overload, the runner still has the tool result. That is where recovery starts. Keep the original call ID and its result, and resend the context needed for that model request.

The diagram starts with the tool result recorded in the session. Placing retries in the runner's model request layer lets that layer reuse the context directly. The chat layer provides a way to resume once the turn has actually ended in failure.

The change added bounded backoff for temporary capacity errors. When the server supplies a retry delay, the runner keeps its existing handling. With no server delay and enough request budget, it retries up to twice, waiting about 5 seconds and then 15 seconds, with up to 1 second of random jitter each time. The wait can be canceled. A quota error still ends the turn. These delays are specific to this implementation. If overload persists, backoff adds to the time before the user sees the terminal error.

Resume the same session when retries run out

If the turn ends with a capacity error and already has a session ID, proj-bot asks the user to reply “continue” in the same chat thread. The host starts a new turn with that session ID, reuses the recorded tool results, and checks authorization against the new message. The session ID retrieves context. The new message still determines what the agent is allowed to do.

One case needs an extra step. A tool may have applied the write just before the runner lost the connection and missed the result. On resume, read the target state first. Proceed to verification for a change already in effect. Execute the step under the current authorization only if the read confirms it did not take effect. If the state is still unclear, report the specific step that needs checking. That decision relies on the target system. The experiment below covers the path where the tool result is already in the session.

Use an append to test recovery

A local HTTP fixture had the real agent runner append one x to a temporary file. The fixture returned overload when it received the next request carrying the tool output. Appending makes a replay visible as xx. The test checked three things: the file held a single x, the recovered requests still carried the output for the original call, and the recovered turn produced the expected reply and one successful terminal event. For a resume in a new process, the test also compared the session IDs.

  • Baseline. The request carried the tool output, and overload ended the turn. The file held one x.
  • Retry within budget. The retry kept the tool output, and the original turn completed. The file held one x.
  • Resume after exhausting retries. The original turn failed. A new process completed a new turn with the same session ID and tool output. The file held one x.

The comparison used the 0.161.0 runner and a patched build based on that same version. A separate local WebSocket fault test also passed. The file still held one x, and the reconnect request retained the original tool-call context. The write counts came from local fault injection. In a separate live-model check, two resumes in new processes recovered a marker that a tool had read in the first turn.

When you add retries to your own agent, start with a small experiment. Inject a model error after a countable write, check where the request picks up, and count what actually happened at the target. The session, the reply, and the write count together show whether that recovery path worked as intended.
