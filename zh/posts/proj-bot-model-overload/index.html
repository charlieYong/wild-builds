模型过载后，如何让 Agent 继续任务并避免重复写入？

charlie · 2026-11-21· 中文

模型过载时，如果工具已经写入成功，就让 Agent 带着原工具结果重试失败的模型请求。重试预算用尽后，保留会话，等用户在原话题续接。这两层恢复各有一个起点，都在已经完成的写入之后。

proj-bot 曾在收到模型容量错误后直接结束当前轮。排查时，我们在一条以 server_overloaded 结束的线上轨迹里看到，失败前已经有多次工具调用返回结果。日志能确认工具结果的存在，具体写入是否生效还要看业务侧。为了把这个问题测清楚，我们用临时文件做了一次可计数的写入，把过载固定注入到紧接着的模型请求。

在原轮次内重试模型请求

一个带工具调用的轮次可以包含多次模型请求。模型先要求调用工具，执行器完成写入，再带着工具结果向模型发出下一次请求。过载出现在这次请求时，执行器仍持有工具结果。恢复点就在这里。保留原来的调用标识和对应结果，重新发送这次推理所需的上下文。

图中“工具结果进入会话”是恢复的前提。把重试放在执行器的模型请求层，可以直接利用这段上下文。聊天层负责在这一轮确实失败之后提供续接入口。

这次修改为临时容量错误加了有限退避。服务端给出重试时间时沿用原有策略。在没有服务端时间、请求预算允许时，最多自动重试两次，本地等待约 5 秒和 15 秒，每次最多再加 1 秒随机抖动。等待可以取消。额度不足仍按终态错误处理。这些等待时间是此次实现的配置，实际持续过载时，用户会多等一段退避时间才看到失败结果。

预算用尽后，在原会话续接

如果容量错误成为当前轮的终态，且已有会话 ID，proj-bot 会请用户在原话题回复「继续」。宿主用这个 ID 启动新一轮，带回已经记录的工具结果，并按新消息重新检查授权。会话 ID 用来找回上下文，当前消息仍决定这次允许做什么。

有一种情况需要多一步。工具可能已经写入，但执行器在收到回执前就断开了。续接时先回读目标状态。已经生效的步骤继续后续验证，确认未生效的步骤才按当前授权执行，仍查不清时就明确报告哪一步待核对。这个分支靠业务回读判断，下面的实验覆盖的是工具结果已经进入会话的路径。

用追加操作检验恢复

本地 HTTP 夹具让真实的 Agent 执行器往临时文件末尾追加一个 x，收到带工具输出的后续请求时再返回过载。用追加操作是因为重复执行会留下 xx。测试同时检查三处证据：最终文件只有一个 x，恢复后的请求仍带原调用对应的工具输出，以及恢复轮有预期答复和一个成功终态。用新进程续接时还要比对前后的会话 ID。

  • 修改前。 过载请求已携带工具输出，当前轮直接失败。文件有一个 x。
  • 预算内重试。 重试请求保留工具输出，原轮次完成。文件有一个 x。
  • 用尽后续接。 原轮以过载结束，新进程用同一会话 ID 和原工具输出完成新轮。文件有一个 x。

对照使用的是同一个 0.161.0 执行器基线和基于它构建的修补版本。另一次本地 WebSocket 注入也通过了重连检查，文件仍只有一个 x，重连请求保留了原工具调用的上下文。写入次数来自本地故障注入。我们另用真实模型在新进程中做了两次同会话续接，验证能找回首轮工具读出的标记。

给自己的 Agent 加重试时，可以先做这个小实验：在一个可计数的写操作后注入模型错误，检查恢复请求从哪里继续，再看目标端到底执行了几次。会话、答复和写入三处都对得上，才能证明这一条恢复路径按预期工作。
